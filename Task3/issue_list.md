Сервисы core-app и ins-comp-settlement получают данные о доступных продуктах через REST API сервиса ins-product-aggregator. В момент вызова он:
- запрашивает информацию из всех **страховых компаний** (сейчас их **пять**),
- агрегирует её в единый список,
- возвращает этот список в рамках того же синхронного запроса.

Чтобы ускорить работу сервисов, при изначальном проектировании команда решила **хранить локальные реплики данных** о продуктах и тарифах в сервисах core-app и ins-comp-settlement.

Сервис core-app осуществляет запрос к ins-product-aggregator 
- раз в 15 минут, 

ins-comp-settlement 
- раз в сутки (ночью), при формировании реестра оформленных страховок. 

Иногда команда сталкивается с ошибками взаимодействия между этими сервисами. Они связаны с **задержками** ответов или **ошибками** при взаимодействии с **API страховых компаний**.

Дополнительно сервис ins-comp-settlement 
- **раз в сутки** осуществляет запрос в core-app по REST API для **получения всех оформленных за день страховок**. Эти данные он использует. 

В ближайшее время InsureTech планирует подписать агентское соглашение ещё с **пятью** страховыми компаниями. 

# Вероятные проблемы и риски
1. Длительная обработка или отказ при обработке запроса страховыми может замедляет или ломает объединённый запрос к ins-product-aggregator.
2. Увеличения числа интеграций ещё больше увеличивает вероятность замедления обработки запроса.
3. Если вдруг выполнение запросов к страховым выполняется последовательно, то это многократно повышает вероятность превысить интервалы, отведённые на получение ответа.
4. Если единый ответ в текущей реализации должен обязательно содежрать информацию от всех страховых, то это неприемлемым образом завязывает работоспособность приложения на инфраструктуру взаимодействия с партнёрскими страховыми.
5. Так как запрос от core-app и ins-comp-settlement синхронный, то ожидание данных может приводить к существенному замедлению работы приложения, сбоям сценариев из-за срабатывания таймаутов, функционированию с устаревшими данными.
6. core-app и ins-comp-settlement получают одни и те же данные с разной периодичностью, создавая в оммент запроса от ins-comp-settlement пиковую нагрузку (видимо поэтому ночью и запускается, чтобы сбои получния данных от информационных систем партнёрских страховых как-то проскочить).
7. Вероятная несогласованность данных core-app и ins-comp-settlement до обновления со стороны ins-comp-settlement, из-за чего в оформленном реестре данные о доступных продуктах могут не соответствовать данными на момент оформления через core-ap (добавили рекламный продукт, по нему оформили, а затем поменяли или убрали).
8. Каждый единый запрос получает обрабатывает и передаёт полный набор данных от всех партнёров, даже если не было изменений, что создаёт излишнюю нагрузку, при увеличении количества партнёрских страховых в два раза возрастёт и избыточная нагрузка.

**Итог**: основные риски связаны с возможными рассинхронизацией данных и отказами, связанными с таймаутами внешних API и ростом нагрузки.

# Предлагаемое решение

1. Перевести ins-product-aggregator на регулярное получение обновлений данных партнёрских страховых компаний, сохранение в свою базу данных и оповещение о наличии обновлённой информации через брокер core-app и ins-comp-settlement.
2. Реализовать возможность получение изменений, что позволит уменьшить нагрузку и ускорить приведение баз сервисов в консистентное состояние.
3. Взаимодействие по взаиморасчётам со страховыми также перевести на асинхронное взаимодействие (отдельный топик).
4. Использование патерна Transactional Outbox реализацией внутри сервисов:
 - для core-app при оформлении страховки и публикация события для взаиморасчётов.
 - для ins-product-aggregator при сохранении данные о доступных продуктах в свою БД перед публикацией событий.
